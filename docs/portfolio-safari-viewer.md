# Safari 打开与切换照片专项 · 2026-10-27

用户定位：电脑 Safari，最明显的问题在打开和切换照片。此前首页滚动检查、in-app browser 的平均回调数字，不能代替这条流程的验证。

## 改动

- 照片入场/离场改用 `Element.animate()` 的 transform/opacity 关键帧，保留弹性、轻微形变和自然比例。拖动仍直接跟随手指/鼠标；自动切换不再逐帧用 JS 计算这些变换。实现参考 [WebKit 原生动画说明](https://webkit.org/blog/10266/web-animations-in-safari-13-1/)。
- 高清原图只在动画结束且停留约1.1秒后按需加载；开始下一次切换/拖动时移除原图层。原图本身没有重编码或降低质量，运动时使用1280预览。
- 缓存最多五个实际解码的预览图对象。最新选择优先，取消旧请求；相邻预览依次加载，不再同时挤入动画。投机预取失败不会去下载大原图。
- 打开相册时将互不依赖的数据库读取并行执行，并预加载 URL 实际选中的第一张预览。
- 修复短拖动松手后被点击处理器误判为翻页；小于24px的拖动不触发甩动翻页。明确拖动、点击、方向键与水平滑动继续可用。

## 同一 Safari 的生产版对照

1512×770，DPR 2。修改前后分别预热一次，再用同一批原生键盘操作连续向右六次；每次操作后读取辅助功能状态。20秒窗口，最终都到第7张。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 相册组件就绪 / 完整导航起点 | 897ms | 399ms |
| 全窗口最长回调间隔 | 82ms | 42ms |
| 动画期间回调 P95 | 31ms | 29ms |
| 动画期间超过25ms的回调间隔数 | 16 | 14 |
| 全页面回调 P95 | 18ms | 18ms |
| 输入排队 P95 | 16ms | 16ms |
| 六次选择的预览解码等待 P95 | 1ms | 13ms |
| 动画期间 DOM 照片像素估算峰值 | 8.3MiB | 8.3MiB |

本次主要改善是打开等待、最重的回调顿挫和动画/大原图的资源分离；不能声称所有指标都明显改善。更保守的预取使快进时的解码等待略增，旧照片会保留到新预览就绪。

另一次 Safari 停留后操作检查观察到4566×3044与4608×3072原图，DOM照片像素估算峰值61.4MiB；这解释了需要将原图从运动层中分离。该检查与上表不是同一个协议，不把它当成进程内存降幅。

这里只记录本机、少量操作、热缓存的结果。辅助功能读取也可能干扰回调节奏；回调间隔不是GPU实际呈现帧率，更不是全程60/120帧保证。`presented`表示预览解码完成并提交照片状态，组件就绪也不是入场动画结束。原始时间序列与限制见 [结构化结果](portfolio-safari-viewer.json)。
